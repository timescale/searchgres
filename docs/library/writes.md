# Writing records

Open an index before writing:

```ts
const index = await openIndex(sql, "docs_index", {
  embedding: openai.embedding("text-embedding-3-small"),
});
```

## Write one record

```ts
const result = await index.upsert(
  {
    content: "Authentication tokens rotate every 24 hours.",
    tree: "docs.auth",
    name: "token-rotation",
    meta: { source: "runbook" },
    temporal: [new Date("2026-08-26T14:30:00Z")],
  },
  { onConflict: "replace" },
);

console.log(result);
// { id: "019ce89d-...", status: "inserted" }
```

`upsert()` is the one-record wrapper around the bulk `upsertMany()` primitive.

## Write a batch

```ts
const results = await index.upsertMany(
  [
    {
      content: "First record",
      tree: "docs.example",
    },
    {
      content: "Second record",
      tree: "docs.example",
      embedding: [/* exactly index.dimensions finite numbers */],
    },
  ],
  { onConflict: "ignore" },
);
```

Results are ordered to match the input:

```ts
type UpsertResult = {
  readonly id: string;
  readonly status: "inserted" | "updated" | "skipped";
};
```

`upsertMany()` accepts at most 1,000 records. It validates the batch in
TypeScript and calls the index's `batch_upsert` routine, which binds a small
constant number of parallel arrays through `unnest` rather than one SQL parameter
per record.

## Record input

```ts
type UpsertRecord = {
  id?: string; // UUIDv7 when supplied
  content: string;
  meta?: Record<string, unknown>;
  tree?: string; // raw dotted ltree; defaults to root ""
  temporal?:
    | readonly [Date | string]
    | readonly [Date | string, Date | string];
  name?: string | null;
  embedding?: readonly number[];
};
```

Rules:

- IDs generated by searchgres and caller-supplied IDs must be UUIDv7.
- `meta` defaults to `{}` and must be a JSON object.
- `tree` defaults to the ltree root, `""`.
- `name` defaults to `null`.
- Embeddings must contain finite numbers and exactly match `index.dimensions`.
- Temporal strings must be ISO-8601 with an explicit offset or `Z`.
- `[t]` is stored as the point `[t, t]`.
- `[start, end]` is stored as `[start, end)` and requires `start < end`.

## Conflicts and identity

```ts
await index.upsert(record, { onConflict: "error" });   // default
await index.upsert(record, { onConflict: "ignore" });
await index.upsert(record, { onConflict: "replace" });
```

Identity rules:

- A named record uses `(tree, name)` as its idempotency key, even when it also
  supplies an ID.
- An unnamed record with an explicit ID uses that ID as its idempotency key.
- An unnamed record with no ID is anonymous and always inserts.
- A fresh named record retains a supplied UUIDv7 ID.
- A named conflict retains the existing record ID.

`"error"` rolls back the entire batch if any input conflicts. `"ignore"` returns
`"skipped"` for a conflicting input. `"replace"` updates only when data differs;
an unchanged replacement returns `"skipped"`.

Duplicate supplied UUIDs, duplicate `(tree, name)` keys, and batches where an ID
key and a name key resolve to the same existing record are rejected as
`InvalidConfigError` before mutation.

## Async and precomputed embeddings

The database triggers support both write paths:

| Input behavior | Stored behavior |
| --- | --- |
| Insert with no embedding | Embedding remains null and a queue row is created. |
| Insert with an embedding | Embedding is preserved and no queue row is created. |
| Content update without replacing embedding | Old embedding is cleared, `content_version` advances, and queue work is created. |
| Content update with a different embedding | New embedding is preserved, `content_version` advances, and no queue row is created. |
| Metadata/tree/name/temporal update | Logical version/hash advance; no queue work is created. |

This behavior also applies to direct SQL producers writing the index tables.

## Calling the routine from SQL

The write path lives in a schema-local PL/pgSQL routine, `batch_upsert`, created
with the index. It is `security invoker` and callable directly, so SQL producers
get the same conflict contract as the library:

```sql
select ord, id, status
from docs_index.batch_upsert(
  array[null]::uuid[],                 -- ids (null → generated UUIDv7)
  array['First record']::text[],       -- contents
  '[{}]'::jsonb,                       -- one JSON object per record
  array['docs.example']::ltree[],      -- trees
  array[null]::tstzrange[],            -- temporals
  array['intro']::text[],              -- names (null → unnamed)
  array[null]::halfvec[],              -- embeddings (null → queued)
  'error'                              -- 'error' | 'ignore' | 'replace'
);
```

The routine returns one `(ord, id, status)` row per input, in input order. It
raises `unique_violation` (SQLSTATE `23505`) for an `'error'` conflict and
`invalid_parameter_value` (`22023`) for malformed input (unequal array lengths,
duplicate keys, or an id/name pair that targets the same existing record). The
library maps these to `ConflictError` and `InvalidConfigError`.

Because the routine body is part of the immutable schema format, a change to its
semantics requires creating a new index and reindexing.
